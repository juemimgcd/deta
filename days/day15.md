# Day 15：核心对照验收与工程交付

[总览](summary.md) · [前一天](day14.md) · [项目目标](../target.md)

## 核心问题

已经能跑任务、保存会话、生成摘要和输出评测报告，怎样判断这一版真的完成了？展示一条成功回答不足以说明 Loop 顺序正确，报告一个通过率也不足以说明所有计划都执行过。

今天收束前十四天的同一条实现链：逐项核对核心语义，修复有证据的问题，完成一条真实 Badcase 的闭环，再把运行方式、已验证能力、Pi 差异和限制交给下一位使用者。没有对应证据的项目保持未验证，不因为到了 Day 15 就改成已完成。

本页仍是实施指南，不是已经执行完这些验收的报告。参考答案提供记录方法和文档结构，真实数值与产物链接需要在实际实现、运行之后填写。

## 先沿一个真实任务走完全链路

```text
用户任务与允许修改范围
  → 最小 CLI 或 AgentSession.prompt
  → Session 登记 Run、提交输入
  → Loop 准备请求
       Session Entry → ContextView
       项目指令、已启用技能、工具声明
       必要时准备压缩 → 摘要 → 事务提交 → 重建请求
  → 实际模型请求与完整响应
  → 参数校验、执行意图、串行工具、配对结果提交
  → 下一轮或结束决策、清理、Run 终态保存
  → 最终代码与项目已有检查
  → Trace / Badcase / 隔离评测
```

选择一项原本就需要读取文件、修改代码并执行已有检查的真实任务，沿这条链标出函数调用和产物位置。没有发生压缩的短任务可用于验证主链路，但压缩部分仍需要另一条实际发生压缩的长任务记录。

不要强行把所有边界塞进一条录屏。正常任务、取消、恢复、超长用户任务和语义错误可能需要不同记录；它们应使用同一套实现与明确版本，而不是分别运行五个互不相干的演示程序。

## 先认识本日的证据对象

| 对象 | 回答的问题 | 不能单独证明什么 |
| --- | --- | --- |
| 代码版本与资源指纹 | 当时运行了哪份实现、提示词和资源 | 该版本已经通过真实任务 |
| Session / Run / Entry | 哪些事实成功提交，工具结果是否结清 | 模型最终看到了所有原始历史 |
| 请求 artifact | 最终消息、系统指令和 schemas 是什么 | 模型一定遵守了要求 |
| Trace / 事件 | 操作顺序、耗时、失败与调用关系 | 缺失 Span 对应的操作没有执行 |
| Compaction 产物 | 选择范围、摘要、尾部、usage 和提交关系 | 压缩后的实际任务结果正确 |
| Badcase | 预期与实际、定位依据、修复和复跑状态 | 写了根因文字就已证明根因 |
| protocol / observations / report | 全部计划、每次试验及版本比较 | 小样本表现可以外推到所有 Coding Agent 任务 |

证据记录至少带时间、代码版本、验证方式、输入来源、结果、产物引用和限制。一个请求失败可能没有完整 usage，一条 Trace 可能没有正常导出结束 Span；未知和缺失必须保留。

## Loop 对照验收

检查调用顺序及其结果，不只比较类名。

| 行为 | 需要观察的事实 | 主要位置 |
| --- | --- | --- |
| 临时流与完整响应分离 | 流分片不逐条进入 Session；完整 AIMessage 提交后才处理工具 | `model.py`、`loop.py` |
| 首次请求准备 | Run 开始时读取资源快照；第一次请求也安装 Context、资源、指令和工具表 | `runtime.py` |
| 后续轮次准备 | prepare_next_turn 在后续轮次执行；结构重建不多调用一次 | `loop.py` |
| 同一份工具声明与执行表 | 响应对应的 plan.tools 同时决定发送 schemas 与执行器 | `hooks.py`、`runtime.py` |
| 助手与工具顺序 | 助手提交 → 参数/前置 Hook → intent 提交 → handler → 最终结果提交 | `loop.py`、`tools.py`、`session.py` |
| 截断、无效参数和业务失败 | 不执行截断调用；已有调用得到明确配对失败结果；普通工具错误可修正 | `loop.py`、`tools.py` |
| Steering / Follow-up | 工具后处理 Steering，自然结束前处理 Follow-up；one/all 不被额外轮询破坏 | `agent.py`、`loop.py` |
| 显式结束与继续 | end 优先于队列；continue 只保证一个后续请求，不与工具续轮叠加 | `loop.py` |
| 批次终止 | 全部最终工具结果都要求终止才停止自然工具续轮 | `loop.py` |
| prompt / continue_ | 新输入与合法历史继续分开；空历史、助手末尾和缺失工具结果遵守既定规则 | `agent.py`、`runtime.py` |
| 重试与预算 | SDK 内部重试关闭；实际尝试、摘要请求、工具额度和总时限各自可查 | `model.py`、`types.py` |
| 取消与收尾 | 模型/工具取消传递，bash 子进程收尾，终态提交后才释放运行占用 | `agent.py`、`builtin_tools/bash.py` |

显式结束、自然停止、limited、cancelled、failed 的原因分别记录。某个 Listener 普通异常被隔离，不代表必须成功的 Session 提交也可以被忽略。

## Context 对照验收

| 行为 | 核对方法 |
| --- | --- |
| 事实与视图分开 | 对比 Session 原条目与 ContextView，构建请求没有原地改写 Entry |
| 最近摘要展开 | 只有最新 summary、按 retained_entry_ids 还原的尾部和之后新增消息；旧摘要覆盖内容不重复追加 |
| retained_entry_ids 来源 | ID 存在且顺序递增，由原始条目还原正文；运行时提交前检查没有孤立 ToolMessage |
| 自定义条目 | context_note 明确标为历史备注；未知类型不猜测投影并留下排除原因 |
| 异常响应 | 流失败的临时消息没有冒充已提交完整响应；Run 和 Trace 保留失败说明 |
| 请求 Hook | 保留或重排 ContextItem 时保留 ID；新增或改写明确标记 hook，拒绝冒用原始来源 |
| 系统资源和工具 | 压缩后仍重新安装；最终指令/schema 的开销计入预算 |
| 资源更新时机 | 同一 Run 使用相同资源快照；下一 Run 才读取规则变更，手动压缩独立读取一次 |
| usage 适用性 | 模型、前缀、指令与工具指纹一致时才能复用；否则回到估算 |
| 最终发送内容 | 从 Entry → ContextItem → 提供方消息逐条解释，并以实际 request artifact 为准 |

资源版本只能证明加载身份，不能代替最终指令正文。若关闭正文采集，说明无法完整复查当次模型输入；若 Hook 删除了规则，应把差异定位到该 Hook，不能归咎于 Session 丢失。

## Compaction 对照验收

| 场景 | 必须保留的结果或失败边界 |
| --- | --- |
| 普通多任务首次压缩 | 合法切点、首次摘要、连续尾部；原始记录仍在 |
| 已有摘要的第二次压缩 | 旧摘要单独更新，上次尾部与新增消息重新选范围 |
| 单个很长的用户任务 | history 可以为空，turn_prefix 单独摘要，近期工具批次保留 |
| 无新 history、但有旧摘要 | previous_summary 不因空 history 丢失 |
| 文件操作信息 | 区分请求涉及路径、结果失败或未知、实际磁盘效果 |
| 手动触发 | 空闲维护占用期间拒绝启动新 Run，调用方收到明确 outcome |
| 阈值触发 | 同一触发点不重复生成；重新准备请求不重复消费队列 |
| 提供方溢出 | 识别结构化错误码，单个逻辑请求最多恢复一次；其他 400 错误不误判 |
| 摘要取消或失败 | 不保存部分候选；已提交事实与提交前取消分开解释 |
| 摘要最后一次响应用量触限或未知 | 启用 token 上限时，提交前立即停止；手动压缩也遵守此边界 |
| 快照变化或写库失败 | 拒绝旧准备对象或回滚事务，旧会话仍可读取 |
| 空记录、工具未结清、刚压缩、无范围 | 对应状态准确，不用空摘要伪装成功 |
| 摘要输入或候选仍过大 | 明确停止，不递归无限压缩或偷偷截断工具消息 |
| 压缩后真实续接 | 查看后续实际请求，再验收任务约束和最终产物 |

压缩前后 token 数是对应视图的估算；摘要调用 usage 是提供方报告值。两者在记录里分栏，不用估算差值冒称真实账单节省。成功生成 summary、成功提交 Compaction Entry、后续任务成功，是三个需要分别核对的事实。

## Session、观测、回放与评测一起核对

| 范围 | 关键证据 |
| --- | --- |
| 中断恢复 | announced 表示尚未开始；intent 无结果表示外部效果未知；不自动重放副作用 |
| 存储失败 | 完成声明以终态保存为前提；结果与工具状态在同一事务更新 |
| 事件与 Trace | CLI 和评测均订阅 artifact_listener；相同采集设置下事件来源可对应，两个独立实例不串身份；Span 缺失仍明确记录 |
| 正文与脱敏 | 采集开关、失败/跳过统计和脱敏限制可查；子 Span 不自动保存异常正文 |
| 资源读取 | Run 开始时加载失败使运行失败；逐文件核算总额度，manifest 与请求使用相同快照，不把漏读当成规则缺失 |
| 录制回放 | 索引封口、完整性、参数顺序、消费终态全部核对；缺失时明确拒绝 |
| 隔离真实复跑 | 独立工作区和数据库，调用正式 AgentSession；先固定产物再评分，检查命令越界改写产物时评分无效 |
| 版本报告 | 批内 Trial 身份与计划一致；代码双环境按 task_id/repeat 人工配对并保留两边 ID；缺失和异常保留，阻塞配对不发布整体提升 |

首版回放的已知范围是新会话、仅消费初始 prompt、完整成功的边界记录；运行中追加输入、失败流、取消时间窗与恢复历史导入仍受 Day 13 的限制，起始资源必须匹配。首版评测直接实现同一代码上的提示词对比；代码修复按 Day 14 的独立环境流程和人工配对表验收。取消、恢复、队列与特定压缩边界另列真实运行证据，不能用普通文件任务的通过率代替。

观测验收覆盖本地 Span、共享事件记录、运行清单与正文采集状态。精确 Span 丢失计数、异步正文导出、通用正文尺寸预算和标准 GenAI 字段映射属于后续范围，交付时写明；同步 I/O 的阻塞限制也要保留。

## 完成一条真实 Badcase 闭环

按以下顺序推进同一 case_id，并让每一步能指向原有或新产生的记录：

1. **定位。** 写明原任务、预期、实际文件或检查结果，引用最早偏离点的请求/响应/工具/Context 证据。证据不足时保留待确认，不先编造根因。
2. **修复。** 只修改根因所在的最小必要路径，说明具体触发条件、以前发生什么、现在怎样处理。若改的是提示词，版本清单也要更新。
3. **原案例复跑。** 从同一份干净初始项目启动真实模型与工具，复用原验收口径，保留新 Run/Trace。不能用修复后已经改好的工作区当初始状态。
4. **固定任务回归。** 按 Day 14 已冻结的协议执行。代码修复固定两个代码环境并保存人工配对表；提示词修改使用批内版本比较。保留成功、失败、未开始、缺失和评分器异常，不为得到更好数字临时删任务或放松评分。
5. **关闭或继续调查。** 原案例和回归都有相应通过证据时标 verified；如果仍失败或有退化，保留 fixed/diagnosed 等真实状态，并记录下一步。

录制回放可以帮助定位和核对调度，但不能代替第 3 步。没有找到真实 Badcase 时，今天的闭环验收仍未完成；不能把人为编造的异常、静态代码阅读或一次成功运行改名为真实失败定位。

## 交付时怎样说明项目

项目说明从三个具体问题展开：

1. **做了什么。** 根据当前源码说明自己实现的 Loop、Session、Context、Compaction 和工具调度；四个基础工具按本计划直接接入完整实现。LangChain 承担模型通信、消息转换与流分片合并，说明自己完成的集成与验证，以及 SDK、OpenTelemetry 等依赖承担的部分。
2. **怎样证明。** 选择一条完整 Trace、一次带来源范围的压缩、一条真实 Badcase 闭环和一份完整版本对比报告，说明输入、调用顺序和结果。
3. **还有什么限制。** 说明验证样本、未知 usage、缺失记录、目录隔离与安全沙箱的区别、Pi 差异和未实现范围。

若只有静态检查与录制回放，就按这个证据层级描述。真实任务验收尚未完成时，版本继续处于实施或验证阶段；不通过增加抽象类、更多文档篇幅或未经验证的提升数字补足交付标准。
