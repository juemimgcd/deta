# Deta：15 个阶段的实现路线

## 1. 范围与完成标准

本计划依据 [项目目标](../target.md)，把 Deta 的首个完整版本划分为 15 个按依赖推进的阶段。重点是尽量还原 Pi 的 Loop、Context 和 Compaction 设计，并完成 Trace、badcase 定位与评测回归闭环。

保留 `day1.md`～`day15.md` 的文件名和 Day 编号，作为稳定的章节索引；每章可以用多个工作日完成。Day 7、Day 12、Day 13、Day 14 按章内步骤推进。某一步的关键验收未通过，先解决问题再推进，不以删除核心语义换取按日完成。

截至 2026-10-01，Day 1–14 的累计实现已写入 `src/deta`，Day 15 的交付文档已创建。各章仍保留阶段练习与参考答案；实际使用见 [README](../README.md)，检查结果和未验证项见 [验收记录](../docs/verification.md)。模型端到端、压缩续接、回放和评测批次仍需真实运行验收。

本版范围：一个模型提供方、一个 Python 包、串行工具、单会话路径、本地存储、最小命令入口。前端、并行工具、会话分支、多 Agent、跨会话 Memory 和远程 RPC 按 `target.md` 的后续范围处理。

**四个基础工具直接提供。** read、write、edit、bash 及文件操作辅助函数均使用完整现成实现，内部算法选读。学习与手写重点放在模型消息、工具 schema、参数校验、调度、结果配对、Loop、Session 和 Context；使用现成工具仍需核对真实接入结果。

**模型接入使用 LangChain 原生类型。** 直接用 ChatOpenAI、HumanMessage、AIMessage、ToolMessage；AIMessageChunk 的 `+` 合并分片。工具 args 是字典，由 Pydantic 校验业务字段。Deta 只定义 Run、Session、预算等业务结构，自己实现 Loop、Context、Compaction；不再维护消息副本类、转换函数或 ChatOpenAI 子类。Day 2 的 open_model 只管理 HTTP 资源。

**参考代码按执行步骤组织。** Day 4 固定单工具执行器，Day 6 提供 execute_tool_batch，Day 7 的主循环直接调用它们；prompt/continue_ 共用取消收尾。Day 9 单独校验保留尾部；Day 11 单独处理摘要请求；Day 14 分开批次调度与单次试验。新增函数对应完整步骤，不新增服务类；队列优先级、事务、重试、取消与事件顺序仍按原契约执行。

每个阶段的交付应能回答三件事：新增了什么可用行为、用什么输入验证、还有什么没有验证。静态检查、录制数据回放和真实模型运行分别记录。

前七章按依赖一次组装：Day 1 建立数据与入口；Day 2 完成单次模型请求；Day 3 一次提供四个工具；Day 4 固定调度器与运行契约；Day 5 接请求预算；Day 6 完成历史配对与整批执行；Day 7 最后写主 Loop 并安装 Agent、runtime 和 CLI。四个工具先齐备，调用方随后出现，避免写完 Loop 后再为新增工具反复修改接口。

接着由 [Day 8](day8.md) 接入持久化事实与恢复，[Day 9](day9.md) 从同一 Session 构建可解释的模型输入，[Day 10](day10.md) 复用该视图选择压缩范围。摘要生成、提交与自动续接在 [Day 11](day11.md) 接入，准备对象本身不代表已经完成压缩。[Day 12](day12.md) 补齐项目资源与观测，[Day 13](day13.md) 建立 Badcase 定位与录制回放，[Day 14](day14.md) 完成隔离评测与版本比较，[Day 15](day15.md) 收束核心验收和工程交付。

第一次做失败修复闭环时，先完成 Day 13 的案例定位和模型边界接入，再做 Day 14 的单任务复跑与小批回归，随后回到 Day 13 完成严格录制回放。Day 14 依赖 Day 13 的接入补丁，但不导入 `replay.py`；尚未完成回放时保持该能力未完成，Day 15 再统一核对。

## 2. 架构：一个包，明确的状态归属

### 2.1 从调用方看系统

```text
Python 调用方 / 最小 CLI
          │
          ▼
AgentSession（runtime.py：组装与会话编排）
          │
          ▼
Agent（agent.py：活动运行、队列、取消、订阅）
          │
          ▼
run_loop（loop.py：请求与工具的执行顺序）
          │
          ├─ 请求准备 ─→ Context ─→ 必要时 Compaction
          │                ▲               │
          │                └──── Session ←─┘
          │                         │
          │                         ▼
          │                    SQLiteStore
          │
          ├─ 模型请求 ─→ model.py ─→ ChatOpenAI ─→ 模型 SDK
          │
          └─ 工具调用 ─→ tools.py ─→ read / write / edit / bash

Trace 与诊断产物：在上述明确边界采集，不负责推进 Loop。
评测与隔离复跑：调用同一 AgentSession，不另写一套 Agent。
```

这里的箭头表示调用与数据流。`loop.py` 通过已绑定的回调完成请求准备和消息提交，不直接导入 Session、SQLite 或 Compaction。

### 2.2 每个状态由谁管理

| 对象 | 唯一职责与状态归属 | 不负责什么 |
| --- | --- | --- |
| `Agent` | 当前运行、临时流式消息、队列、取消和进程内状态 | SQLite、摘要算法、终端渲染 |
| `run_loop` | 一次 Run 内的轮次、工具续轮与结束顺序 | 配置加载、持久化格式、评测 |
| `AgentSession` | 组装 Agent 与服务，绑定请求准备、消息提交和压缩流程 | 再实现一套 Loop 或摘要算法 |
| `Session` | 已提交会话记录、未完成工具状态、恢复语义 | 调用模型、选择摘要切点 |
| `SQLiteStore` | 表结构、事务、记录读写 | 判断是否继续运行或重新执行工具 |
| `ContextView` | 本次模型输入与来源映射，属于派生视图 | 拥有另一份可独立修改的持久化历史 |
| `CompactionPreparation` | 切点、待总结历史、轮次前缀、保留尾部等准备结果 | 自行写库或启动后台任务 |
| Trace / Artifact | 观测记录、输入快照及诊断证据 | 作为任务恢复的事实来源 |

Day 8 接入 Session 后，持久化历史以 Session 为准；Agent 的消息是本次运行的内存视图，不能与 Session 各自独立追加同一条最终消息。`AgentSession` 在明确的提交步骤保存记录，并在请求前安装最新上下文。

初始存储方案采用单一本地 SQLite，利用事务一起提交工具结果与状态变化。该选择是本计划对 `target.md` 存储待定项的建议落点；不同时实现 JSONL、SQLite、PostgreSQL 三种后端。Span 使用 JSONL 导出，小批评测计划与结果使用 JSON 文件。

### 2.3 一次请求中的具体数据

```text
Session Entry
  └─ id、顺序、类型、消息或摘要内容
          ↓ context.py
ContextView
  └─ AgentMessage[]、条目来源、摘要信息、预算估算
          ↓ 请求前调整
最终 AgentMessage[] + ToolSpec[]
          ↓ model.py 转换
提供方请求消息 + 工具 schema
          ↓ 记录请求快照并调用 SDK
ModelEvent 流
  └─ 文本增量、工具参数增量、最终 AIMessage
          ↓ loop.py
完整 ToolCall → 参数校验 → 工具执行 → ToolMessage
          ↓ AgentSession / Session 提交
下一次 ContextView
```

`types.py` 定义跨模块消息契约；`events.py` 定义 Agent 对外生命周期事件。工具参数在各内置工具文件定义，存储记录在 `session.py` 定义，压缩准备对象在 `compaction.py` 定义，避免所有类型都堆进一个文件。

## 4. 控制复杂度的约束

1. **单包、单进程、单存储。** 不建设服务拆分、容器编排或通用存储仓库层。评测需要隔离时只为具体试验提供环境。
2. **以普通函数和少量对象为主。** 保留有状态的 Agent、AgentSession、Session 和存储对象；上下文投影、切点选择和统计尽量写成明确输入输出的函数。
3. **只有真实替换需求才抽接口。** 模型和工具执行边界需要支持真实调用与录制回放；不为每个内部函数建立 Protocol、工厂和注册器。
4. **有限 Hooks，直接绑定。** Loop 的准备、提交、结束步骤可使用带类型的回调。无需通用插件加载器、装饰器扫描或事件驱动工作流引擎。
5. **状态只有一个主人。** Loop 不保存第二份会话，Trace 不承载恢复状态，Context 不修改原始历史。
6. **实现逐日增强，不复制多版核心。** 使用同一个 Loop 和模型边界；不保留 `simple_loop`、`session_loop`、`compact_loop` 三套算法。
7. **文件按职责拆分。** 核心模块可以平铺；当某部分有独立算法或状态且已影响阅读，再拆文件。不追求最少行数，也不提前搭建多层目录。
8. **Pi 语义与 Python 写法分开。** 必须保留的执行顺序和边界写进对照记录；命名、类结构和语言机制不做逐行翻译。

## 6. 分阶段实施计划

### Day 1：工程入口与数据契约

**目标：** 定义一条执行链上的对象与责任，建立最小开发入口。

**涉及文件：** `pyproject.toml`、`cli.py`、`types.py`、`events.py`、包入口、配置示例与忽略规则，开始记录 `docs/pi-alignment.md`。

- 配置包入口和项目使用的格式、静态检查命令，按需选择并锁定依赖。
- 定义用户消息、助手消息、工具调用、工具结果、usage、结束原因与运行结果。
- 定义少量生命周期事件；说明模型流事件与 Agent 事件之间的转换关系。
- 明确 Run、模型 Turn、实际请求 Attempt，以及 Compaction 中“用户任务片段”的区别。
- 配置由入口读取后显式传入，核心模块不在导入时读取环境变量或启动服务。

**验收：** help/version 可用，公共入口可导入；能以一个“读取文件”的例子说明每个对象由谁产生、交给谁、何时进入历史。今天不宣称 Agent Loop 已完成。

**Pi 对照：** `types.ts` 中的消息、事件和工具契约；只吸收本版实际需要的数据。

### Day 2：单次流式模型请求与基础 Trace

**目标：** 先把一次真实请求做完整，让后面的 Loop 复用同一通信边界。

**涉及文件：** `model.py`、`observability/tracing.py`、`observability/artifacts.py`，更新入口及消息类型。

- 用 langchain-openai 接入一个提供方，完成 JSON 消息投影、bind_tools、astream、块合并、最终消息、usage 和停止原因。
- 单次接口不执行工具、不自行循环；完整保留模型返回的工具调用信息。
- 接入 OTel 上下文与本地导出；区分逻辑请求和实际尝试。若无法观测 SDK 内部重试，先关闭它，不能把推测次数记作真实 Attempt。
- 保存配置版本与最终请求快照引用，正文采集可关闭、可脱敏；没有正文时明确诊断限制。

**验收：** 一次真实文本请求正常结束，Trace 能关联输入、响应、耗时和 usage；鉴权或配置失败有明确错误，未知 usage 不显示为零。不记录密钥。

### Day 8：Session、SQLite 与恢复边界

**目标：** 将可用的内存 Agent 接入可靠本地会话。

**涉及文件：** `storage.py`、`session.py`、`runtime.py`、入口与诊断关联。

- 定义 Entry、运行记录和未完成工具记录。数据格式带版本，SQLite 事务接口保持具体。
- AgentSession 在执行工具前提交意图，结果返回后将结果与状态更新放在同一事务中。
- 加载会话后重建内存视图；处理缺失结果再允许继续。
- 崩溃窗口中结果未知的工具不自动重放，写入明确中断说明；新执行关联旧 Run 与会话。
- 支持读取已记录的事件时间线，作为基础轨迹查看；更完整的回放放到 Day 13。

**验收：** 正常退出重启后继续任务；分别检查执行前、执行中和结果提交附近的中断状态。数据库保存失败不被报告为任务成功。

**Pi 对照：** `harness/session/`、工具意图与结果提交、恢复时的未知结果处理。

### Day 9：Context 投影、转换与来源映射

**目标：** 从完整会话重建可解释的模型输入。

**涉及文件：** `context.py`、`session.py`、`runtime.py`、`model.py`、请求快照。

- 明确 Entry → AgentMessage → 提供方消息的转换，区分自定义条目、异常响应与普通消息。
- 支持从最近 Compaction 条目展开摘要、retained_entry_ids 指向的尾部和新增消息的数据形状，实际摘要生成在后两天接入。
- 分开 Context 构建、请求前调整和提供方转换；保存最终请求快照及来源关联。
- 处理系统指令和工具声明，避免上下文重建后丢失；过滤后保证工具消息配对。
- 实现预算估算：最近有效 usage 加其后新增内容估算，明确输出预留和估算限制。

**验收：** 给定固定会话记录，能逐条解释最终输入来源；不会重复加入摘要覆盖的历史，也不会修改原始 Entry。最终快照与实际发送内容对应。

**Pi 对照：** `harness/session/context.ts`、`harness/messages.ts`、请求边界的转换顺序。

### Day 10：Compaction 的切点与准备算法

**目标：** 先把压缩输入选择做对，再调用模型摘要。

**涉及文件：** `compaction.py`、`context.py`、对照记录。

- 按 token 保留目标从后向前寻找合法切点，不从孤立工具结果切开。
- 找出切点所在用户任务的起点；若切在该任务内部，拆分较早历史、该轮前缀与保留尾部。
- 准备对象包含已有摘要、上述消息范围、文件操作信息和估算，不发模型请求、不写库。
- 为下一次压缩正确展开上次 retainedTail，避免丢失或重复总结。
- 明确空记录、刚完成压缩、没有可压缩范围和极长单条内容的结果。

**验收：** 检查普通多轮、超长单轮和已有摘要三类记录的范围选择；能解释每条消息为何被摘要或保留，工具配对有效，准备过程无副作用。

**Pi 对照：** `findCutPoint`、`findTurnStartIndex`、`prepareCompaction`。

### Day 11：Compaction 生成、提交与续接

**目标：** 把准备算法接回正式运行，使长任务真正继续。

**涉及文件：** `compaction.py`、`runtime.py`、`session.py`、模型与观测接入。

- 摘要使用同一个单次模型边界，但使用独立摘要提示词与预算，不运行 Coding Agent 工具循环。
- 实现首次摘要、结合旧摘要的更新、单轮前缀摘要及结果组合；保留目标、约束、进度、决策和文件信息。
- 分开准备、生成和提交。成功后保存 Compaction Entry 与 retained_entry_ids，失败不覆盖旧会话。
- 接入手动、阈值和溢出三种触发，保留阈值去重和有界溢出恢复。
- 重建 Context 再检查预算；分别记录摘要输入范围、usage、压缩前后规模和后续实际请求。

**验收：** 真实长任务及超长单轮压缩后继续；已声明的任务约束仍满足；取消摘要、模型失败和写库失败不会保存半成品。重试不陷入无限压缩。

**Pi 对照：** `compactWithRequest`、摘要与更新提示词、结构化步骤中的阈值和溢出恢复。

### Day 12：项目指令、Skills 与观测补齐

**目标：** 提供真实项目资源，并把新增流程纳入同一诊断链。

**涉及文件：** `resources.py`、`runtime.py`、`context.py`、`observability/`、运行清单。

- 定义项目指令的目录作用范围和合并顺序，记录加载来源。
- 每次 Run 开始时读取一份资源快照，后续请求与自动压缩复用；规则变更在下一次 Run 生效，手动压缩单独读取一次。
- 提供 Skills 的名称、描述和路径，正文按需读取，技能相对路径按技能目录解析。
- 核对 Trace 覆盖请求准备、实际尝试、工具处理、Session 写入和 Compaction。
- 记录资源、提示词和 schema 版本；检查正文采集与脱敏、导出失败、有界刷新、缺失数据标记。
- CLI 和评测入口显式安装同一个事件监听函数；精确 Span 丢失计数、异步正文导出和标准 GenAI 字段映射留到后续需求。
- 同时运行两个独立 Agent，检查 Trace 父子关系、事件来源和取消隔离；这不要求实现多 Agent 编排。

**验收：** 一个项目规则能影响实际任务，技能按需读取；压缩前后关键资源仍有效。两个独立运行不串 Trace，观测导出失败不改变执行结果。

**Pi 对照：** Skills 的渐进加载；telemetry 的上下文传播设计，区分已落地代码与设计文档。

### Day 13：Badcase 定位与回放

**目标：** 把执行失败转化为可调查、可复查的问题。

**涉及文件：** `observability/artifacts.py`、`observability/replay.py`、最小诊断入口。

- 完善 badcase 数据：预期与实际、任务环境、初步分类、关联 Span、根因证据、处理状态。
- 先定位一个真实失败并接通 Day 14 的复跑入口；严格录制回放在首次小批回归之后完成。
- 支持查看一条运行的时间线，并下钻到请求快照、工具输出和上下文变化。
- 通过已有模型与工具执行边界注入录制响应，回放调度逻辑；保留调用参数、顺序和完整性检查。
- 缺少记录、参数不匹配或脱敏破坏必要数据时，明确拒绝完整回放，不回退到真实请求或工具。
- 区分程序报错与无异常但结果不正确；允许根因尚未确认。

**验收：** 选取真实失败记录，能解释从现象到证据的定位过程；离线回放不调用外部模型、不修改原工作区。不能用录制回放结果宣称真实模型成功。

**Pi 对照：** 借鉴观测与会话关联；badcase 管理和录制回放作为 Deta 增加的能力记录。

### Day 14：隔离评测与版本比较

**目标：** 用固定任务和验收口径衡量真实改动。

**涉及文件：** `evaluation/runner.py`、`graders.py`、`report.py`，逐步建设 `evals/` 中的任务与初始项目。

- 从已有人工验收与真实 badcase 整理约 10～20 个任务，包含成功标准、约束和运行预算。
- 每次试验复制干净初始工作区，调用正式 AgentSession，隔离会话和运行数据；普通目录复制不等同于安全沙箱。
- 根据最终文件、已有检查和任务约束评分。验收逻辑与基准数据不暴露为可由 Agent 随意修改的工作内容。
- 记录预先计划的全部试验，保留失败、缺失和评测器异常；每条结果能下钻到 Run / Trace。
- runner 直接支持同一代码上的提示词版本对照；代码改动按 Day 14 的双环境流程运行，核对协议后按任务和重复编号配对。记录耗时与 token，货币成本没有可靠计价依据时标为未计算；语义评分按具体任务增加。
- 汇总预算消耗，完善 token 预算与重复失败检测，并将策略触发纳入报告。

**验收：** 一批任务能够重复执行且没有工作区串扰；一个已知正确产物和一个已知错误产物可检查验收器；对照报告不隐藏未完成试验。小样本结论说明范围。

**Pi 对照：** `packages/evals/` 中的任务计划、隔离、重复试验和完整结果报告；不迁移它的工具链。
